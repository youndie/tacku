# B-17 — MCP по HTTP: сервер авторизации и метаданные защищённого ресурса

Пока MCP живёт на stdio, агент живёт рядом с пользователем, и командный сценарий «агент дежурит по
бэклогу, пока команда спит» невозможен. Снять ограничение можно только вместе с авторизацией: по
спеке MCP-сервер на HTTP **обязан** реализовать OAuth 2.0 Protected Resource Metadata (RFC 9728) и
проверять, что токен выпущен именно для него как для аудитории (RFC 8707), и **не имеет права**
принимать никакие другие токены.

- **Транспорт — не работа, работа — авторизация.** Проба показала, что обработчик streamable HTTP
  монтируется на тот же `ServeMux` одной строкой; всё остальное в этой задаче — сервер авторизации,
  выдача токенов с аудиторией, скоупы и `403` с `insufficient_scope`.
- Отвергнуто: принимать общий `Bearer` KOMPOT-клиента и назвать это MCP. Работать будет, называться
  соответствующей реализацией — нет. Заявлять соответствие, которого нет, — ровно та болезнь,
  которую этот проект пытается вылечить у KOMPOT.
- Не покрывает: выбор конкретного сервера авторизации. Это первое решение внутри задачи.

- AC: посторонний MCP-клиент проходит полный путь — `401` с `WWW-Authenticate`, метаданные ресурса,
  метаданные сервера авторизации, токен с аудиторией — и вызывает инструмент; токен для другой
  аудитории отвергается.
- Anchors: `server/internal/mcp/`, `server/internal/auth/`.

**Закрыто 21.08.2026.** Первое решение внутри задачи — **сервер авторизации остаётся
конфигурацией**: спека MCP выносит его реализацию за скобки, tacku реализует сторону ресурса.
Метаданные по RFC 9728, проверка подписи по JWKS издателя, проверка issuer и срока — и **проверка
аудитории**, которой не делает за нас никто: middleware SDK смотрит подпись, срок и скоупы, а «этот
токен выпущен для нас» проверяет только наш верификатор. Это MUST спеки и единственное, что отличает
ресурс-сервер от того, кто просто смотрит на подпись.

Скоупы решены не отказом, а видимостью: у токена без `tasks:write` инструменты записи отсутствуют в
`tools/list` — механизм, на который указывает сама спека ([Q-15](../research/questions.md)), потому
что `403 insufficient_scope` живёт на уровне HTTP-запроса, а все вызовы делят один адрес.

Побочно закрыт риск, который был бы дороже всего: **личность переехала из процесса в запрос**. Обе
поверхности кладут принципала в контекст, фолбэк-актор остался только у stdio и над HTTP равен `nil`
намеренно. Тест, доказывающий это, — единственный, где фолбэка нет вовсе: изменение атрибутируется
исключительно из токена, вместе с версией сборки.

Обе главные проверки прогнаны **мутацией**: снятая проверка аудитории роняет тест о чужом ресурсе,
подстановка субъекта вместо принципала — тест о токене без `on_behalf_of`.
