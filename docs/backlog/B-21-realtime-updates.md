# B-21 — Канал живых обновлений: делать ли его на прототипе

Протокол описывает кадр точечного обновления компонента и оставляет транспорт на усмотрение
реализации; в референсной — SSE. Для трекера, где пишут агенты, живые обновления выглядят почти
обязательными: доска, которая не меняется, пока её не перезагрузишь, в таком продукте ощущается
сломанной.

- **Почему это `question`.** Переносимой проверки на канал нет: `text/event-stream` — не
  JSON-документ, и в слепой обход набора он не входит, о чём README говорит прямо. Значит SSE,
  сделанный на прототипе, останется **непроверенным вторым стеком** — то есть не служит приёмочной
  цели проекта, только продуктовой.
- Отсюда развилка, которую надо решить явно, а не по инерции: либо канал делается ради продукта и
  честно помечается как непроверяемая часть, либо вместо него делается проверяемое — например
  переспрос по курсору по таймеру, — и это осознанно хуже, но измеримо.
- Требование, которое нельзя пропустить в любом варианте: топик обязан быть персональным везде, где
  персональны данные. Общий топик означает утечку обновлений одного пользователя другому.
- Не покрывает: собственную переносимую проверку канала. Это задача в адрес kompot, если решим, что
  она нужна.

- AC: решение принято и записано с причиной; если «да» — обновление задачи агентом доезжает до
  открытой доски без перезагрузки, а топик персонален.
- Anchors: `server/internal/realtime/`, `client/app/src/`.
