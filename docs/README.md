# docs — tacku

Лёгкий командный таск-трекер с двумя равноправными поверхностями: люди работают через экраны,
которые целиком описывает сервер (BDUI-протокол KOMPOT), агенты — через MCP-инструменты. Документация
слоистая, ссылки идут сверху вниз.

```
[ Ресёрч — почему архитектура такая, а не другая ]
                     │
[ Фича (бизнес + BDD) ] ──▶ [ Экран клиента ]
                                    │
                                    ▼
                          [ Эндпоинт API (контракт, уровень доступа) ]
                                    │
                                    ▼
                          [ Сервис (владение данными, деплой) ]
```

| Слой | Каталог | На что отвечает | Источник истины |
|---|---|---|---|
| Ресёрч | `research/` | *почему* так построено; что проверено, что гипотеза | артефакты, названные у каждого факта |
| Фича | `features/` | *что* система делает и *зачем*; BDD-сценарии | этот репозиторий |
| Клиент | `screens/` | что видит пользователь: состояния, действия, навигация | код клиента |
| API | `api/` | адрес, метод, уровень доступа, где живёт контракт | код сервера |
| Сервис | `services/` | кто владеет данными, зависимости, деплой, локальный запуск | этот репозиторий |

**Сейчас существует только слой ресёрча, и это не пропуск.** Кода нет; фича, экран, эндпоинт и
сервис, написанные до кода, описывали бы намерение в виде факта. Каталоги появятся вместе с кодом,
который они описывают, — по одному документу на сущность, с путями в код.

**Бэклог** — [backlog.md](../backlog.md): индекс и решения; сами задачи лежат по файлу на штуку в
[`backlog/`](backlog/) и цитируются как `[B-12](backlog/B-12-date-field-module.md)`.

**Дизайн** — [`design/`](design/), вне слоёв намеренно: адресован человеку, а не агенту, и описывает
границы, а не устройство.

| Документ | Что в нём |
|---|---|
| [design-brief.md](design/design-brief.md) | бриф: в каких границах вообще рисуется интерфейс и почему |
| [design-review.md](design/design-review.md) | сверка присланного макета с **машиночитаемым** профилем: шесть расхождений и два вопроса к протоколу |
| [design-spec-tokens.md](design/design-spec-tokens.md) | набор токенов из макета — исходник для констант клиента |

## Соглашения

- **`id`** во фронтматтере уникален и равен имени файла.
- Ссылки между слоями — идентификаторы во фронтматтере и обычные markdown-ссылки в теле.
- Один документ — одна сущность.
- BDD-сценарии пишутся из кода, а не по памяти: настоящие коды ответа, настоящие тексты ошибок.
  Пока кода нет, сценарий помечается как *целевой*.
- **Главный потребитель — кодовый агент.** В каждом документе есть якоря — пути к каталогу,
  обработчику, модели, — чтобы читатель добирался до кода за один переход. Не дублировать то, что
  живёт в коде: копия гниёт, путь — нет.
- **Язык.** Документация по-русски. Код, комментарии, имена тестов, тексты ошибок, сообщения
  коммитов и корневой `README.md` — по-английски. Идентификаторы, адреса и имена HTTP-заголовков —
  дословно как в коде.

## Барьер

У этого репозитория есть правило, которого нет у обычного проекта: **Go-сервер пишется по
опубликованному контракту KOMPOT, а не по его Kotlin-исходникам.** Читать `SPEC.md`, файлы схемы,
README набора проверок и эталонный корпус можно и нужно; читать `*.kt` реализации — нет. Вопрос,
ответа на который в контракте нет, записывается в [журнал вопросов](research/questions.md) до того,
как решается.

Правило объяснено в [ресёрче §0](research/research-architecture.md#0-правило-барьера). Оно не про
чистоту, а про то, ради чего проект вообще существует.
